## 0. 总纲：三条铁律（血的教训）

| # | 铁律 | 违反的代价（本项目的真实账单） |
|---|---|---|
| 1 | **先取证，后动手**。原厂固件活着的时候，是这台机器唯一愿意主动告诉你真相的时刻 | 我们早期没抓 `swapp` 运行时日志，靠 boot 日志猜 sensor 型号 → **猜错（SC4336P → 实为 OS05L10）**，白干整整两周，19 篇文档全部带错并需回炉订正 |
| 2 | **型号/结论必须有"运行时证据"（实机探测 / 原厂 app 日志），并且用离线解包逆向交叉验证**（§2.5） | boot 日志 `sensor0: sc4336p` 只是 `sys_config.ko` 的 module param 默认值，原厂自己也默认这个 → 信它导致整个排查方向（供电/复位/板级驱动）全错 |
| 3 | **每一层都要有可观测判据，没过闸就别往下调** | WiFi 在 `phy80211` 软链出现之前就配 IP，直接打崩模组 TX 路径，设备冻结 → 多次物理断电救回；sensor 在没证明"器件在 I2C 总线上"之前去怀疑供电 → 得出"缺板级供电"的错误结论 |

**一句话**：移植 80% 的工作量在"摸清原厂到底做了什么"，只有 20% 在"把第三方改对"。
省下的取证时间，会以十倍代价在调试期还回来。

## 1. 准确判断硬件型号

### 1.1 先记住：这些东西**不能**当证据

| 不可信来源 | 为什么不可信 | 本例 |
|---|---|---|
| boot / dmesg 里的 `sensor0: sc4336p` | 那是内核模块 `sys_config.ko` 的 **module param 默认值**，只决定"用哪套时钟/引脚表"，**与真实硬件无关**。原厂自己的 `load3516cv610_debug` 默认也是 `sc4336p` | 我们被它坑了两周；紧跟着的 `parse sensor[sc4336p] failed!` 其实已经在暗示"板级表里并没有这颗"，当时没读懂 |
| SDK / 第三方固件的 sensor 源码目录列表 | 目录里有什么，只说明**第三方支持什么**，不说明**板子上焊了什么** | 第三方只有 gc4023/gc8613/sc431hai/sc4336p，板上是 os05l10 |
| 参考文档里"某某与之 pin-to-pin 兼容" | 兼容 ≠ 同型号。寄存器表、bayer 相位、AE 地址都可能不同 | os04d10 只出现在我们驱动头注释里（模板名），不是硬件型号 |
| IQ 参数目录名"只是复用"这种猜测 | 目录名恰好等于原厂 app 里唯一的驱动名与模式名时，那是**巧合概率为零**的强证据 | `/system/resource/scene_param/sensor_os05l10/` |
| 单一来源的"三重印证" | 三条证据若**同源**（都来自同一个默认值），三条其实只等于一条 | 我们早期的"三重印证"经复核三条全不成立 |

### 1.2 可信度金字塔（从强到弱）

```
  ① 实物丝印 / 模组标签 / 拆解照        ← 物理事实，最强（但常看不到）
  ② 实机 I2C 探测 + 芯片 ID 回读         ← 器件自己报身份
  ③ 原厂 app 运行时日志（判型结果行）     ← 原厂自己探测后的结论
  ④ 原厂 IQ 资源目录名 / 模式名符号        ← 编译进去的配套资源
  ⑤ 原厂二进制里的驱动符号（symtab）      ← 编进去的驱动函数名
  ⑥ 出厂配置 defaultparam.txt             ← 厂商填写的机型/分辨率
  ⑦ 实际出图分辨率 / 码流能力             ← 反推（4M 驱动出不了 5M）
```

**判定规则：至少拿到 ② 和 ③ 中的一项，才算定案。** 只有 ⑥⑦ 属于"猜测"。

### 1.3 实机判定动作（按这个顺序做，10 分钟内定案）

```sh
# ① 扫总线——注意：必须用"-r"（快速/原始探测），且要先把时钟和 pinmux 恢复好
i2cdetect -y -r 0 ; i2cdetect -y -r 1 ; i2cdetect -y -r 2

# ② 回读芯片 ID（OS05L10 有 bank 概念，先选 bank 再读）
i2cset -y 0 0x3c 0xfd 0x00
i2cget -y 0 0x3c 0x02 ; i2cget -y 0 0x3c 0x03 ; i2cget -y 0 0x3c 0x04 ; i2cget -y 0 0x3c 0x05
# [本例] 05 53 01 01 → OmniVision OS05L10，与原厂 swapp 日志逐字节一致
```

**[本例] 关键判别表**：

| 探测地址(7-bit) | 应答 | 结论 |
|---|---|---|
| `0x3C` 应答、ID=`05 53 01 01` | ✅ | **OS05L10**（5MP，2880×1620） |
| `0x30` 应答 | — | SC4336P（4MP，2560×1440） |
| 全总线无应答 | ⚠️ | **先怀疑"探测条件不对"，不要先怀疑器件不在**（见 §4.6 假阴性） |

> **本例最大的坑**：早期 `i2cdetect` 全空，被解读为"传感器没供电/没复位"。
> 真相是：当时用 SC4336P 的地址 `0x30` 去探（没人应答，理所当然），
> 且上一次 `sample_venc` 尝试把时钟/pad 打回了错误状态。
> 换成 `0x3C` 后**器件立刻应答** —— 供电、pinmux、MCLK 一直都是好的。
> **⇒ 探测无应答 ≠ 器件不存在，只说明"这条 (地址, 时序) 组合下没人回话"。**

**实机不方便时（设备已刷第三方 / 不想刷机），走离线逆向定型号**，见 §2.5：
解原厂 rootfs → 搜 app 与 so 里的 sensor 符号 → 看 IQ 资源目录名 → 看 init 表模式名。
**[本例]** 正是靠这条路发现"第三方固件里根本没有 OS05L10 驱动"这一根本缺口。

### 1.4 SoC / 外围也要一并定死

| 对象 | 怎么定 | 为什么必须定死 |
|---|---|---|
| SoC 型号与封装 | `defaultparam.txt` 的 `chip_name` + 官方 PINOUT 表 | **[本例]** QFN 封装实际引出的 GPIO 只有 51 个（最大 gpio63）；我们曾花时间扫 GPIO 69–87，**芯片上根本没有这些管脚**，纯属无效劳动 |
| NAND 型号/参数 | 丝印（DS35Q1GA）+ `/proc/mtd` + 页/OOB 尺寸 | 决定 UBIFS/ubinize 参数与分区布局；PEB 128KiB / page 2048 / OOB 64 写错 rootfs 直接挂载失败 |
| WiFi 模组形态 | `lsusb`（USB）vs `lsmod`/DTB（SDIO/PCIe） | **[本例]** WS73 是 **USB** 模组，`lsusb` 出 `ffff:3733`；形态决定上电方式与驱动加载链 |
| 有无有线网口 | 实物 + `ifconfig -a` | 本例**无网口** → 出事只能走串口/TF 卡，工具链要提前备好 |
| 串口参数 | 实物测量 + 试 | 3.3V TTL / 115200 8N1；接错电平直接烧 UART |

## 2. 原厂固件正常运行时，必须收集哪些信息

### 2.0 取证有两条腿，缺一条就会变成猜谜

| 腿 | 手段 | 回答的问题 | 局限 |
|---|---|---|---|
| **A. 运行时取证** | 串口/SSH 抓日志、状态、寄存器快照（§2.1–2.4） | "它**实际做了**什么"（判型结果、注入的 SSID、真实写的寄存器值） | 设备必须活着；窗口有限；抓不到"编进去但没跑到"的东西 |
| **B. 离线静态逆向** | 分区 dump 后解包 + 二进制反汇编/符号分析（**§2.5**） | "它**编了**什么"（驱动支持列表、init 表、板级初始化、内建驱动） | 静态看不到运行时注入值；可能碰到加密镜像；结论必须回实机验证 |

**[本例] 两条腿缺一不可**：
- 只靠 A（早期）：boot 日志写着 `sc4336p`，猜错型号，白干两周；
- 补上 B：从解包的原厂 rootfs 里找到 `swapp` 只有 `os05l10` 驱动、IQ 目录是 `sensor_os05l10`、
  并用 ELF 解析抠出 **209 条 init 寄存器表** —— 这才是补驱动的原料；
- 再回到 A 验证：按 `0x3C` 探测器件立刻应答、芯片 ID 与原厂日志逐字节一致 —— 定案。

**⇒ 顺序建议：先做 A（快、便宜、不可逆），再做 B（慢、但能拿到 A 拿不到的东西），最后用 A 验证 B 的推论。**

### 2.1 时机：必须在"原厂 app 真正跑起来之后"抓

很多关键行为**只在运行时发生**，静态解包看不到：

- sensor 型号是 app **探测后**判定的（不是配置写死的）；
- 时钟、pinmux、复位序列是 app **逐个寄存器写**出来的；
- WiFi 的 SSID/PSK 是 app **运行时注入** wpa_supplicant 的，配置文件里根本没有；
- IQ 参数是按判定出的 sensor 名**动态加载**的目录。

```sh
# [本例] 拿原厂 root shell 的正确姿势（不刷机、不改 env）
#   串口拦 U-Boot → 只改运行时变量，绝不 saveenv
setenv bootargs "$bootargs init=/bin/sh" ; boot
mount -o remount,rw /
/system/etc/init.d/start_swapp.sh &     # 手动把原厂系统拉起来（这一步才产生真相）
sleep 20
```

**抓取的黄金窗口**：原厂 app 起来 20–60 秒内。抓完再刷机。

### 2.2 必抓清单（照单抓，漏一项后面就要猜）

| 档 | # | 抓什么 | 命令 | 为什么不抓会吃亏 |
|---|---|---|---|---|
| **必抓** | 1 | **原厂应用自身日志** | `cp /xxx/applog/swapp*.log /tmp/` | **[本例决定性证据]** `sensor[0]: type(11), name(os05l10)` + `i2c_dev:0, dev_addr:0x78 ... = 05 53 01 01`。**这一份日志直接终结了两周的型号之争** |
| 必抓 | 2 | I2C 探测 + 芯片 ID | `i2cdetect -y -r 0/1/2`、`i2cget` | 硬件身份的终审判决 |
| 必抓 | 3 | 应用写的**寄存器序列**（不是状态，是行为） | 日志里的 `sensor_clk/sensor_rstn/i2c_muxer reg_addr=…` 行；或 `strace` 抓 ioctl | **[本例]** 由此得到 `0x17940040=0x1212`、`0x17940050=0x1137`、`0x17940098/9c=0x1135`、CRG `0x11018440` 先 `0xa010` 后 `0x4010`。**注意这些 pad 地址与 SDK 引脚表给的不一致** —— 以运行时打印为准 |
| 必抓 | 4 | 内核 cmdline / 分区表 | `cat /proc/cmdline`、`cat /proc/mtd`、U-Boot `printenv` | 决定刷机布局与 bootargs。**[本例]** 原厂 15 分区 A/B 与第三方 4 分区互不兼容，不处理 env 就必砖 |
| 必抓 | 5 | 模块清单 + **加载顺序** + md5 | `cat /proc/modules`、`md5sum *.ko` | 顺序错了驱动起不来；md5 用来区分"同名不同版本"的 ko |
| 必抓 | 6 | 启动脚本全集 | `init.d/*`、`load3516cv610*` | 谁 insmod 什么、带什么参数、先后顺序的唯一出处 |
| 必抓 | 7 | MPP 运行时状态 | `/proc/umap/vi`、`/proc/umap/isp`、`/proc/umap/sys` | 分辨率、raw 位宽、bayer 相位、fps、pipe 数 = 出图的验收基线 |
| 必抓 | 8 | **整包分区备份** | 见 §2.3 | 刷坏了没有第二次机会 |
| 应抓 | 9 | 寄存器区间快照 | `insmod sazreg.ko mode=4 raddr=… rcnt=…`（`/dev/mem` 常被驱动占用读不到 CRG/GPIO，必须走内核模块） | 与第三方做 `regdiff`，差异行就是答案 |
| 应抓 | 10 | GPIO 状态 | `/sys/kernel/debug/gpio`、`/sys/class/gpio` | 找出上电/复位脚 |
| 应抓 | 11 | 板级配置全集 | `driver.txt`（机型→驱动映射）、`defaultparam.txt`、`gpio/*.json`、各类 ini | **[本例]** `driver.txt` 给出 `SAZ1051 → wifi_soc.ko + motor_mx2208a.ko`；`defaultparam.txt` 给出 `chip_name`、`hardware_type`、`sensor_stream_size=1620` |
| 应抓 | 12 | **IQ 参数目录** | `tar cf /tmp/iq.tar /system/resource/scene_param/` | **[本例]** `sensor_os05l10/` 4 个 ini **可直接复用到第三方固件**，省掉整轮画质调参 |
| 应抓 | 13 | WiFi 运行时 | `lsusb`、`wpa_cli status`、`/sys/class/net/wlan0/{phy80211,address}`、`dmesg \| grep -i wifi` | 建立"正常应该长什么样"的基线 |
| 应抓 | 14 | 私有设备节点与其 ioctl | `ls -l /dev/swboard`、`cat /proc/kmsg`、`strace -e ioctl` | **[本例]** 原厂通过 `/dev/swboard` 写 sensor 时钟/复位/I2C 复用寄存器；不抓就不知道它干了什么（后来证明不是必需，但当时不知道） |
| 应抓 | 15 | 内核符号表 | 解压 zImage → 解析内建 kallsyms | 离线反查 **built-in 驱动**（本例导出 31,841 个符号，定位到 `sunniwell_board_init`） |
| **必抓**（第三方缺驱动时） | 16 | 应用二进制符号 + init 表 | ELF symtab + reloc 定位 `g_<sensor>_mode_tbl`；必要时 capstone 反汇编提 `(reg,val)` | **[本例]** 从 `libswhisilicon_adapter.so` 抠出 209 条 OS05L10 init 寄存器 —— **补 sensor 驱动的原料，没有它就无法出图** |

> 现成脚本：`tools/factory_capture.sh`（旧，含本机硬编码地址）
> **通用版：`tools/capture_baseline.sh`**（本文配套新增，无硬编码型号，输出分节快照）

### 2.3 备份：在做任何写操作之前完成，并做双向校验

```sh
# 设备端建立基准
for n in 0 1 2 3 4 5 6 7 8; do printf "mtd%s " $n; \
  dd if=/dev/mtdblock$n bs=64k 2>/dev/null | md5sum; done | tee md5_orig.txt
# 主机端流式导出（用 mtdblock 逻辑块跳坏块，别用 mtdN —— 含 OOB）
for n in 0 1 2 3 4 5 6 7 8; do ssh $D "dd if=/dev/mtdblock$n bs=64k 2>/dev/null" > part$n.bin; done
# 本地 md5 必须与设备端一致，否则别烧
```

**[本例] 两个备份坑**：
- 刷机工具的 `boot` 分区文件**不是**"头 + 裸 u-boot"，而是"头 + 打包（加密/签名）载荷"，
  载荷偏移 `0x800` 处必须是 `2d d2 b4 4b`（裸 u-boot 是 `b8 00 00 ea`，会被拒绝）。
  正确做法：**直接用原样 dump 的 `mtd0.bin`**，别自己拼。
- env 分区格式是 `4B CRC32 + 数据 + 0xFF 填充`，改完必须重算 CRC，否则 U-Boot 认为 env 无效。

### 2.4 容易漏掉、但后来最值钱的三样

1. **应用日志走 stdout**（本例 log4cpp OstreamAppender → `std::cout`），
   不是 `/dev/console`。启动时**必须重定向到文件**才看得到；
   且 `/tmp` 常常只有几十 MB tmpfs，日志要写到持久存储。
2. **出厂驱动映射表**（`driver.txt` 之类）：机型 → 具体用哪个 ko。第三方固件没有这张表，只能靠抓。
3. **多机差异项**：MAC、SSID、静态 IP **在原厂是运行时注入、不落盘**的。
   你在自己机器上抓到的写死值，刷到第二台就会冲突 —— **[本例]** 后来必须把
   `ws73_cfg.ini` 里的 `mac_addr` 删掉（改用芯片 efuse），把 SSID/IP 抽到 `/etc/saz_net.conf`。

### 2.5 离线静态逆向：解包原厂固件与二进制分析

> 适用场景：设备已经刷成第三方回不去了、原厂日志抓不全、或需要拿到"编进去但运行时不打印"的东西
> （sensor 支持列表、init 寄存器表、U-Boot 板级初始化、内核内建驱动）。
> **本例的 sensor 驱动原料（209 条寄存器表）就是纯离线抠出来的。**

#### 2.5.1 解包链路（先把文件系统还原成目录树）

```
分区 dump(mtdblockN) → 识别文件系统 → 提取 rootfs 树 → 再逐个二进制分析
```

| 文件系统 | 识别特征 | 工具 | 备注 |
|---|---|---|---|
| UBI / UBIFS | 头 `UBI#`（v1） | `ubireader`（`ubireader_extract_files`） | **[本例]** 解 system 分区得到 **26 MB** rootfs 树 → `tmp/mtd8_rootfs/` |
| UBI 内 squashfs | bootargs 里 `root=/dev/ubiblock0_0 rootfstype=squashfs ubi.mtd=N` | 先剥 UBI 再 `unsquashfs` | 本例 system_a 就是这种（**只读**，运行时靠上层 tmpfs 覆盖） |
| squashfs 裸镜像 | 头 `hsqs` | `unsquashfs` | — |
| jffs2 / cramfs | 头 `1985` / `28cd3d45` | `jffs2dump` / `cramfsck` | — |

**两个实测坑**：
- Windows 上用 `ubireader` 解包时，符号链接会被提前创建而目标尚未解出 → `WinError 2`。
  解法：monkeypatch `os.symlink` 先记录、解完统一回放（见 `tools/extract_rootfs_local.py`）。
- **别忘了也解 `data` 分区**：应用日志常常写在掉电保存区而不是 `/var/log`。
  **[本例]** 决定性证据 `swapp0.log` 是从 `data`（mtd12）解出来的：`extract_mtd12/…/applog/swapp0.log:475`。

#### 2.5.2 rootfs 树到手后，按这个顺序挖

| 顺序 | 挖什么 | 做法 | **[本例]** 收获 |
|---|---|---|---|
| 1 | **sensor 真实型号** | `strings` + ELF symtab 搜 sensor 名（搜所有 `libsns_*` / `sensor_*` / `*_cmos` 符号） | `swapp` 里 **12 处 `os05l10` 符号、`零` sc4336p**；`libswhisilicon_adapter.so` 有 `g_sns_os05l10_obj`、`OS05L10_5M_30FPS_10BIT_LINEAR_MODE` |
| 2 | **IQ 参数** | `resource/scene_param/` 下的目录名 | `sensor_os05l10/`（4 个 ini）→ **直接复制到第三方固件复用**，省掉整轮调参 |
| 3 | **启动时序** | `init.d/*`、`load3516cv610*` | insmod 清单与参数（`-i -mmz_start/-mmz_size` 等）、`SNS_TYPE0` 默认值、机型→驱动映射 |
| 4 | **机型映射 / 出厂参数** | `driver.txt`、`defaultparam.txt`、`gpio/*.json` | `SAZ1051 → wifi_soc.ko + motor_mx2208a.ko`；`chip_name=HI3516CV610`、`sensor_stream_size=1620` |
| 5 | **ko 版本差异** | `md5sum` 全量比对；ELF 节/符号/**重定位**解析 | `sys_config.ko` 的时钟配置表**逐项与原厂一致** → 直接排除"时钟表不同"假设；`plat_soc.ko` 两版 md5 相同（可直接复用） |
| 6 | **私有板级驱动** | 从 app 二进制字符串挖设备节点与 ioctl 名 | 挖出 `/dev/swboard` + `BOARD_IOCTL_SET_REG_VAL` + `sensor_clk/sensor_rstn/i2c_muxer` |
| 7 | **★ init 寄存器表** | ELF symtab + reloc 定位 `g_<sensor>_mode_tbl` / `<sensor>_linear_*_init`，还原 `{addr,value}` 序列；必要时用 capstone 反汇编 ARM/Thumb 提取 `mov r1,#reg / mov r2,#val / bl write_fn` 三元组 | 抠出 **209 条 OS05L10 上电表** → 生成 `os05l10_cmos.c/h` + `os05l10_sensor_ctrl.c` |

#### 2.5.3 再深一层：U-Boot / 内核 / DTB / 引脚表

| 对象 | 关键手法 | **[本例]** |
|---|---|---|
| **U-Boot（裸 ARM 镜像）** | ① 先推**基址**：异常向量区的字面量池是一串等间距指针（本例 `0x41800060/0xc0/0x120…`）→ base = `0x41800000`；验证方法：以候选 base 统计"指向 NUL 起始字符串"的指针占比（本例 32% vs 其他候选 ≤2%）② 再按 **Thumb-2** 反汇编 | 定位到 `sunniwell boot entry`（file `0x2f894`–`0x2fa64`）：GPIO 组时钟 + `M8556 gpio muxconfig` + GPIO7_6 复位脉冲。**实测重放到第三方固件 → GPIO7_6 拉低立刻断网 ⇒ 这段代码是给 WiFi 模组的，与 sensor 无关**（成功证伪一个错误假设） |
| **内核（zImage）** | 搜 `1f 8b 08` 定位内嵌 piggy gzip 流 → 解压出原始内核；再解析**内建 kallsyms**（自动探测 `kallsyms_offsets` 最长非递减 u32 游程 → 拿 `relative_base`/`num_syms`/`names`） | 解出 `tmp/kernel_factory.bin`（8.2 MB，`Linux version 5.10.221 (root@sw) #1 SMP`）+ 符号表 **31,841 项** → 定位内建驱动 `sunniwell_board_init` |
| **DTB** | 从 FIT 镜像抽出 dtb → `dtc -I dtb -O dts` 反编译 → 全量 grep | 690 行 DTS 里**没有任何 regulator / sensor-power 节点** → 排除"DTB 缺供电"假设 |
| **芯片引脚表** | 官方 PINOUT xlsx 直接解析（`tools/xlsx_read.py`）成机器可读映射 | 证明 **QFN 封装实际只引出 51 个 GPIO（最大 gpio63）** → 之前扫描的 GPIO 69–87 在芯片上根本不存在，纯属无效劳动 |

#### 2.5.4 逆向的边界：别把逆向结论当终审

| 坑 | 说明 |
|---|---|
| 镜像可能加密 | **[本例]** 工厂 `mtd5/mtd6` 内核是加密镜像（头 `a9c43800…`）→ 无法从二进制反查供电 GPIO |
| built-in 驱动拿不到文件 | 内建在内核里的驱动只能靠 kallsyms + 反汇编，无法直接拷贝复用 |
| **抠表有边界风险** | 独立控制函数（`mirror_flip` / `standby` 等）的寄存器写**不能平铺进 init 表**。本例误并入 → `0x32` 落定 `1` = H-mirror → 画面洋红（见 §4.4） |
| "它做了" ≠ "必须做" | **[本例]** 原厂通过 `/dev/swboard` 写一堆寄存器，后来证明**不补这个驱动也能出图**。逆向给的是行为清单，不是必需项清单 |
| 静态看不到动态值 | sensor 判型结果、注入的 SSID、运行时计算的 mmz 参数 —— 只能靠运行时取证 |
| 结论必须回实机验证 | 本例逆向得出 sensor 型号后，仍用 `i2cdetect` + 芯片 ID 回读做了终审 |

## 2.6 整机外设普查：别只盯着 sensor 和 WiFi

> **典型返工**：移植出一个"能启动"的新系统后，才发现云台电机 / IRCUT / 补光 / audio
> 不知道是什么、不知道怎么起来 → 只能重刷原厂重新取证。
> 代价：串口传 26 MB ≈ **45–55 分钟**、96 MB ≈ **2.3 小时**；
> 更贵的是**运行时状态永远丢失**（只留下一堆冷镜像）。

### 2.6.1 别漏项

| 类别 | 外设 |
|---|---|
| 视频 | 主/副 sensor、IRCUT、光敏、红外补光、白光补光、状态指示灯 |
| 运动 | **云台电机**（水平/垂直）、限位开关、驱动 IC |
| 网络 | WiFi（USB/SDIO）、4G、有线网口、蓝牙 |
| 音频 | mic、speaker、audio codec、蜂鸣器 |
| 存储 | NAND/eMMC、TF 卡槽、USB |
| 交互 | 复位键、SD 检测、按键 |
| 其他 | RTC/电池、NPU、加密芯片、温感、红外人体 |

### 2.6.2 每个外设必须回答 6 个问题

① 是什么（型号/驱动名）· ② 怎么上电（常开/GPIO/PMIC/模块内部）·
③ 怎么加载（ko 名/参数/**顺序**/依赖）· ④ 怎么配置（ini/json/GPIO 号/校准数据）·
⑤ 怎么验证（判据命令 + 期望值，**必须能在第三方固件上复跑**）· ⑥ 证据出处。

### 2.6.3 三把钥匙（快速拿到整机清单）

| 钥匙 | 位置 | 得到什么 |
|---|---|---|
| 机型→驱动映射 | `/system/etc/driver.txt`（按 `device_model` 查） | 所有可替换外设的驱动名 |
| GPIO 定义 | `/system/etc/gpio/<model>_gpio.json` | 所有 GPIO 外设编号 |
| 能力开关 | `/system/etc/defaultparam.txt`、`capability/*_capinfo.json` | 有无音频/电机、分辨率、硬件版本 |

**[本例]** 三把钥匙一次给出：`wifi_soc.ko` + **`motor_mx2208a.ko`**（云台）、
`IrCut(-1/-1)`（本机未接）、`IRLed=9`、`WhiteLed=10`、`RedLed=6`、`OthLed=7`、
`Speaker=60`、`Rsetkey=61`、`upg_no_audio=1`（**无音频**）、`motor_reset=1`（有云台）、
`sensor_stream_size=1620`（5MP）。另注意：**`eth0` 是虚接口**，原厂脚本会 `ifconfig eth0 down`。

#### 2.6.4 音频（mic / speaker）：GPIO 通常只是功放使能脚

音频**不是** GPIO 直驱的，链路是
`mic → codec（内置 acodec 或外挂）→ I2S/PCM/PDM → SoC → codec → 功放 → speaker`；
**GPIO 只负责功放使能（PA_EN）/ 静音**，I2C（若有）负责配置外挂 codec。

要摸清：① codec 是内置 `ot_acodec` 还是外挂（型号 + I2C 控制地址）· ② 功放使能 GPIO 与**有效电平** ·
③ `ot_aio/ot_ai/ot_ao/ot_aenc/ot_adec/ot_acodec` 的加载顺序与 **I2S 引脚 pinmux**（常与 sensor/GPIO 复用）·
④ 采样率/位宽/声道（`Speaker_chn=Right`）· ⑤ 能力开关（`upg_no_audio=1` = 无音频）。

> **★ 坑**：`gpio json` 里有 `Speaker:60` **不等于**本机有音频。
> **[本例]** `upg_no_audio=1`（无音频），但 json 仍定义 `Speaker=60`、`Speaker_chn=Right`
> —— 这份 json 是**机型通版**，本型号根本没贴音频器件。**必须看能力开关，别照着 GPIO 去写喇叭驱动。**

> 完整的本机普查结果表见 skill `ipc-firmware-port-playbook`（"参考实例"一节）。

## 3. 搞清网络 / WiFi 启动流程需要什么条件

### 3.1 先分形态：这决定整条链路

| 形态 | 识别 | 上电方式 | 本例 |
|---|---|---|---|
| **USB 模组** | `lsusb` 有 VID:PID | 常由某个 GPIO（`WL_REG_ON`）拉起，或 ko 内部 | **WS73 = USB**，`ffff:3733`；上电靠 `muxfix.ko mode=1` 的 GPIO 序列 |
| SDIO 模组 | `lsmod`/DTB 里有 mmc 节点 | 常由 `mmc` 电源域 + GPIO | — |
| 内置/SoC 无线 | 内核有无线驱动 | — | — |

**第一条要搞清的：模组是怎么上电的。** 上电没做，后面全部免谈，而且症状极具误导性
（"驱动加载成功、网卡存在、但怎么都连不上"）。

### 3.2 依赖链：顺序是硬约束

```
rfkill → libarc4 → firmware_class → cfg80211 → mac80211
      → muxfix(mode=1 skip_usb=1，★单次) → plat_soc → wifi_soc
```

| 约束 | 违反后果 |
|---|---|
| `cfg80211` **必须早于**厂商驱动 | 厂商驱动注册 wdev 时 cfg80211 还不在 → 注册失败 |
| `muxfix` **必须单次**带 `mode=1 skip_usb=1` | 先无参再 `mode=1` 会 `File exists` **静默失败** → 模组从未上电，且不报错 |
| 平台驱动早于主驱动（`plat_soc` → `wifi_soc`） | 反向则 probe 失败 |
| 这些 ko 常是 `[permanent]`，**无法 rmmod** | 换驱动必须 `reboot` 清态，不能指望卸载重来 |

### 3.3 四个必要条件（缺一不可）

1. **内核无线子系统可用且 ABI 匹配**：`CONFIG_CFG80211`/`mac80211`。
   自己编的 cfg80211 若与运行内核 `struct net` 布局错配，会出现极隐蔽的错误
   （**[本例]** `net->genl_sock` 错位 → nl80211 请求全部 `-111 ECONNREFUSED`，
   诊断靠一行 `gs_proto=0 (16=GENERIC,0=ROUTE)` 打印才定位）。
2. **驱动真的把接口登记进 cfg80211**：网卡被创建 ≠ 被登记。
   **[本例]** 出厂 `wifi_soc.ko` 建了 netdev 但没设 `dev->ieee80211_ptr`
   → cfg80211 notifier 首句 `if (!wdev) return NOTIFY_DONE` 直接跳过
   → `SET_INTERFACE` 按 ifindex 查不到 wdev → `-19 ENODEV` → "Could not configure driver mode"。
3. **固件/配置文件路径且先于驱动就位**：
   **[本例]** `plat_soc.ko` 在 **probe 阶段**就要读 `/system/etc/ws73_cfg.ini`，
   文件缺失 → wlan0 根本不注册。**刷机包里漏这个文件 = 刷完 WiFi 直接不起**。
4. **配置段落在驱动真正读取的那个段**：
   **[本例]** `mac_addr` 驱动从 `[HOST_PLAT]` 读（源码 `get_cust_conf_string_etc(INI_MODU_PLAT,…)`），
   我们却写在 `[HOST_WIFI_MAC]` → 读不到 → MAC 全 0。
   而 MAC 的**分隔符逗号本来就是对的**（`pc_sep=","`），差点把对的改错。

### 3.4 判据链：一级没过，绝不下手下一步

| 级 | 判据 | 期望 | 没过意味着 |
|---|---|---|---|
| 1 | `lsusb \| grep <id>` | 模组出现 | **没上电**（查 muxfix/GPIO/供电） |
| 2 | `ls /sys/class/net/wlan0` | 存在 | 驱动没起来 / 固件 ini 缺失 |
| 3 | **`/sys/class/net/wlan0/phy80211` 软链** | `-> ../../ieee80211/phy0` | **wdev 未登记（本例真正的拦路虎）** |
| 4 | `cat /sys/class/net/wlan0/address` | 非全 0 | ini 的 MAC 段/格式问题 |
| 5 | `wpa_cli status` → `wpa_state` | `COMPLETED` | 认证/驱动交互问题 |
| 6 | IP + 默认路由 + `ping` | 0% 丢包 | DHCP/路由/DNS |

> **铁律：`COMPLETED` 之前绝不碰 IP。** 本例在 MAC 全 0 时 `ifconfig up`/`udhcpc`，
> 直接打崩模组 TX 路径，设备冻结，多次靠物理断电救回。
>
> **不要用 `iw dev` 判断接口在不在**：nl80211 的 `GET_INTERFACE DUMP` 里
> `nl80211_send_iface()` 失败会 `continue` **静默跳过**，制造"接口存在"的假象。
> **看 `phy80211` 软链**（这是 cfg80211 的硬逻辑：`phy80211` 存在 ⇔ `ieee80211_ptr` 非空 ⇔ 已进 `wdev_list`）。

### 3.5 搞清"启动流程"的取证动作

```sh
cat /proc/modules                 # 加载顺序（不是列表，是顺序）
grep -rn "insmod" /etc/init.d/    # 谁加载、什么参数
ls -l /etc/wireless/ /system/etc/*.ini
wpa_cli -iwlan0 status            # 连的是哪个 SSID、加密方式
# 关键：原厂 SSID 可能根本不在配置文件里（运行时注入）
cat /etc/wpa_supplicant.conf      # [本例] 只有 ctrl_interface + update_config，无 SSID
```

### 3.6 持久化要注意

- 写成 init 脚本，且**排在 MPP 之后**（本例 `S95ws73` 在 `S90autorun` 之后）。
- 脚本里要有**轮询等待闸门**（等 `phy80211`、等 `COMPLETED`），不能固定 sleep 了事。
- **不要把 MAC / SSID / 静态 IP 写死进固件**：多机同刷会冲突、换网就失效。
  抽成配置文件，缺失时回退默认行为；IP 留空则走 DHCP。

## 4. 摸清 sensor 运行机制

### 4.1 分层模型（按这个顺序理解，也按这个顺序排查）

```
① 供电（常开轨 / GPIO 可控 / PMIC）
② MCLK 时钟（CRG 寄存器）
③ pinmux（CLK / RSTN / I2C SDA,SCL 的功能选择）
④ 复位释放（RSTN 拉高 + 时序）
⑤ I2C 可达（器件应答 + 芯片 ID 正确）      ← ★ 分水岭
⑥ 寄存器初始化表（init table 209 条之类）
⑦ MIPI 输出（LANE / 分辨率 / raw 位宽）
⑧ VI 建 pipe → ISP（bayer/AE/AWB/IQ）→ VENC → RTSP
```

**⑤ 是分水岭**：⑤ 之前的问题叫"器件没活"，⑤ 之后的问题叫"驱动不对"。
本例全部弯路都源于**在没证明 ⑤ 的情况下去怀疑 ①②③④**。

### 4.2 逐级判据表

| 层 | 看什么 | 期望 | 失败含义 |
|---|---|---|---|
| ② MCLK | CRG 寄存器（本例 `0x11018440`） | 使能位置起，频率位正确（本例最终 `0x4010`，启用阶段先 `0xa010`） | 时钟没给 → 器件不工作 |
| ③ pinmux | IOMUX 寄存器（本例 `0x17940040/50/98/9c`） | 值与原厂**运行时打印**一致 | pad 功能选错 |
| ④ 复位 | RSTN GPIO | 释放（拉高）且有时序 | 一直复位中 |
| ⑤ I2C | `i2cdetect` + 芯片 ID | 应答且 ID 对 | 见 §4.6 假阴性 |
| ⑥ init | 应用日志 `I2C_WRITE error` 计数 | **0** | 地址错 / 表错 |
| ⑦ MIPI | `/proc/umap/vi` 的 dev detect | 有设备、分辨率正确 | 模式/LANE 配置错 |
| ⑧ ISP | `/proc/umap/isp` 的 bayer / flip / mirror | 与 sensor 实际镜像状态**一致** | 见 §4.5 洋红 |

### 4.3 I2C 地址位宽铁律（本例第二次致命错误）

```c
/* sensor_common.c */
ret = ioctl(i2c->fd, OT_I2C_SLAVE_FORCE, (i2c->addr >> 1));   /* 内部右移！ */
```

⇒ 这套 SDK 的 `*_I2C_ADDR` **必须填 8-bit 地址**。

| Sensor | `*_I2C_ADDR` | `>>1` 实际寻址 | 结果 |
|---|---|---|---|
| SC4336P | `0x60` | `0x30` | ✅ |
| **OS05L10（错）** | ~~`0x3C`~~ | **`0x1E`** | ❌ 不存在的从机，第一条写就 NAK |
| **OS05L10（对）** | **`0x78`** | `0x3C` | ✅ 读出 `05 53 01 01` |

**症状完全相同**（`cis_write_reg I2C_WRITE error!` → `reg_init failed`），
所以"补了驱动还不出图"时，**第一嫌疑就是地址位宽**，而不是供电。

同理还要注意 **寄存器地址宽度 / 数据宽度**（`ADDR_BYTE`、`DATA_BYTE`、bank 选择机制）。
本例 OS05L10 用 `0xFD` 做 bank 选择，1B 地址 + 1B 数据。

### 4.4 从原厂抠传感器寄存器表的正确姿势

1. **找表**：ELF symtab + reloc 定位 `g_sns_<sensor>_obj` / `g_<sensor>_mode_tbl` / `<sensor>_linear_*_init`。
2. **抠表**：按重定位项顺序还原 `{addr, value}` 序列（本例 209 条）。
3. **★ 边界校验（本例踩大坑）**：
   独立的**控制函数**（`mirror_flip` / `standby` 等）里的寄存器写，**不能平铺进 init 表**。
   本例把 `os05l10_mirror_flip` 的 4 个档位分支误并入 init 表，
   导致表尾 `0x32` 被写成 `00→01→02→03` 的怪序列，最终落定 `0x32=1` = **H-mirror 开** → 画面洋红。
   **⇒ 提取后必须与原厂函数地址范围严格比对边界；表尾出现异常跳变值时，先怀疑混入了别的函数。**
4. **对照验证**：拿原厂日志里的实际读写（dev_addr + reg + value）和你抠出的表比对。

### 4.5 画质：bayer 相位与镜像状态必须一致

- 洋红（缺 G）= **教科书级 bayer/demosaic 相位错位**，不是 AWB 漂移（AWB 还会把它放大）。
- 判据：白墙 ROI 采样，`R-G` / `B-G` 应接近 0（本例正常 +4/+2；洋红 +56/+51）。
- **做单寄存器扫描实验**（活体、可逆、零编译）比反复编译强百倍：
  本例 `tools/magenta_b1_032_scan.py` 在线写 `0x32` 各档位后抓帧量化，
  一次就定出 `0x32=0`（不镜像）正确，且 `=3`（180°）虽颜色对但画面倒置。
- **IQ 参数直接用原厂的**（`sensor_<name>/` 目录），别自己从零调。

### 4.6 "假阴性"——本项目最贵的一课

| 现象 | 错误解读 | 真相 |
|---|---|---|
| `i2cdetect` 三条总线全空 | sensor 没供电 / 没复位 / 缺板级驱动 | 用错了探测地址（`0x30`），且上次尝试把时钟/pad 打回了错误态 |
| 三条 I2C 同时报 `wait idle abort` | 单个 pad 复用错 | 总线被整体钳住（SDA/SCL 被拉低）——**属于现象，不是根因**，同样被错误解读成"电源域没起来" |
| 换入原厂 MPP 模块后 EEPROM(0x3c) 消失 | 原厂模块更"正" | 原厂模块在这块板上**反而更差**：本例 bus0 上原有的 `0x3c` 应答直接消失（已回滚） |

**教训**：
1. 探测前**先把 pinmux + 时钟恢复到已知正确状态**（写一个 `sensor_mux.sh` 固化），否则你在测"上一次失败留下的残局"。
2. **多地址并行探测**（把常见 sensor 地址都试一遍），不要只试你"以为"的那个。
3. 一个假设要**证伪**它，得先有正向证据；"看不到"本身不是证据。
